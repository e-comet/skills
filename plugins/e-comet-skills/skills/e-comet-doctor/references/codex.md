# Codex host actions

Use these actions only after the corresponding Codex surface is observed.

- Codex CLI: `codex --version` identifies the CLI only. When the host reports an untrusted or skipped e-Comet hook, use `/hooks`, review the named definition and trust it: it is the e-Comet plugin's own handler, which Codex asks to trust again after the plugin is installed or updated. Start a fresh CLI session after plugin component updates unless reload was separately observed.
- ChatGPT Desktop with Codex: verify the plugin is present and enabled for the actual trusted project, restart Desktop after local marketplace or plugin file changes, and open a fresh task. Installation does not itself establish trust for bundled hooks.
- Keep CLI and Desktop conclusions separate: their bundled Codex versions can differ. No current verified Windows UI path or command in the accepted evidence identifies the Desktop-bundled version.

`BROWSER_JOB_HANDOFF_REQUIRED` from a signed local tool, or `OZON_AUTHORIZATION_REJECTED` saying the trusted browser-job hook did not provide Ozon authorization, means the hooks did not provide the authorization: call `e_comet_diagnose` with installation scope, `safe_probes`, and `hook_permissions` before any other step and never repeat `browser_job` automatically. Treat a successful result as a saved configuration snapshot for the checked directory. `ready` means every expected native e-Comet handler is enabled and trusted. `not_checked` with `facts.context:"configuration_probe"` means the single bounded inspector did not return an inventory; its closed failure reason and phase describe only that probe boundary and never establish missing, disabled, or untrusted hooks. On observed ChatGPT Desktop with Codex, use Settings → Plugins → Personal → e-Comet MCP Tools → Hooks only for an observed `disabled` or `review_required` handler, enabling the former or reviewing and trusting the latter: they are the e-Comet plugin's own handlers, which Codex asks to trust again after the plugin is installed or updated (README: Trust all). On observed Codex CLI, use `/hooks` for the corresponding observed action with the same explanation. Do not expose raw inspector errors, paths, commands, or server messages. The snapshot does not prove that any handler ran in this task.

An already exposed tool proves availability only in the current task. Parser or loader success alone is not hook execution evidence. If the exact installed build has not been exercised on the observed Codex surface, state that verification gap.

When remote tools are missing while local tools exist, call `e_comet_diagnose` with installation scope, `safe_probes`, and `codex_mcp_auth`. The probe uses one native `codex mcp list --json` configuration snapshot: exact configured server names match our `.mcp.json`, but the CLI does not attest plugin identity or the current Desktop task's runtime state. Read `facts.status`: `not_logged_in` supports only qualified configuration wording; `credentials_present` means stored credentials are unvalidated and needs a real `info` call; `missing`, `ambiguous`, `unknown_status` or `not_checked` support no authorization claim. An `enabled:false` remote entry does not support an active sign-in conclusion. Firm authorization wording requires an explicit host authorization error or notice. When supported, the Desktop action is Settings → Plugins → e-Comet MCP Tools → server E-comet → Connect.

Official sources, verified 2026-09-13: [hooks and trust](https://learn.chatgpt.com/docs/hooks), [CLI and Desktop troubleshooting](https://learn.chatgpt.com/docs/reference/troubleshooting), and [plugin packaging and refresh](https://developers.openai.com/plugins/build/plugins). Accepted local observation confirms that Codex CLI can discover e-Comet hook definitions as untrusted; discovery alone did not prove a trusted lifecycle.
